# Case-Centered Surgical Workflow Architecture Design

日期：2026-05-07

## 背景

当前系统已经形成三个相互关联但职责边界尚未完全固定的业务域：

- 数据管理中台
- 病例工作台
- 手术导航工作区

现有导航相关实现已经具备部分工作区聚合能力，包括：

- `case_manifest.json` 病例清单与阶段目录
- `planning`、`registration`、`navigation`、`evaluation` 阶段结果持久化
- `navigation/workspace_snapshot.json` 页面恢复快照
- `NavigationWorkspaceApplicationService`、`NavigationWorkspaceSnapshotStore` 等工作区编排基础设施

但系统层面仍缺少一份统一规格，明确下面几个关键问题：

1. 骨骼 STL 应该在哪一层首次导入与维护
2. 骨骼 STL、病例、导航工作区之间分别是什么关系
3. 五环节各自负责什么输入、动作、产物和门禁
4. 多骨、多部位、分骨配准与融合导航空间应如何进入系统模型
5. 页面恢复、运行态、正式结果之间的真源边界是什么

这份设计文档的目的，是先从全系统视角固定业务边界和数据关系，再为导航工作区内部编排规格提供上层约束。

## 目标

首版架构规格需要同时解决以下问题：

1. 明确 `数据中台 -> 病例工作台 -> 手术导航工作区` 的职责链路
2. 明确骨骼资产、器械资产、几何文件资产的主数据归属
3. 明确病例与资产之间是“绑定/引用”关系，而不是复制拥有关系
4. 明确导航工作区只消费病例工作包，不承担资产首次导入职责
5. 明确五环节工作流的业务语义、阶段产物和门禁原则
6. 明确多骨、多部位、分骨配准与融合导航空间的数据模型
7. 明确正式结果与页面快照的边界，保证恢复逻辑可解释

## 非目标

本次不纳入以下范围：

- 重写数据中台已有资产导入界面
- 重写病例工作台已有基础 UI
- 展开“服务配准”创新算法的内部数学实现
- 引入全新的后端流程引擎或外部工作流引擎
- 把所有现有导航代码一次性重构为完全新的模块树

## 方案比较

### 方案 A：病例驱动的工作区编排

定义：

- 数据中台负责资产主库
- 病例工作台负责病例与资产的绑定
- 手术导航工作区只消费病例绑定结果并推进五环节

优点：

- 资产、病例、运行态边界清楚
- 复用现有 `case_manifest` 与工作区结果目录最自然
- 最符合当前代码已具备的导航工作区聚合方向

缺点：

- 需要补齐病例绑定层的正式数据模型
- 需要在导航侧严格收敛“临时导入”的能力

### 方案 B：导航页中心化

定义：

- 导航工作区同时承担资产导入、病例绑定和流程推进

优点：

- 交互集中

缺点：

- 主数据和运行态会混在一个页面域里
- 后续恢复、复用、跨病例统计会变得模糊
- 与当前系统已有的中台/工作台分层相冲突

### 方案 C：流程引擎优先

定义：

- 先抽象强状态机或流程引擎，再让三个页面域都成为壳层

优点：

- 长期治理最规范

缺点：

- 超出当前迭代范围
- 现阶段首先缺的是业务边界，而不是状态机框架

### 结论

采用方案 A。

## 总体架构

### 1. 数据管理中台

职责：

- 作为全系统唯一资产主库
- 导入、标准化、版本化、停用资产
- 管理骨骼 STL、器械模型、探针模型、几何文件等主数据

约束：

- 不负责病例流程推进
- 不负责导航运行态
- 不保存探针标定、配准结果、导航记录等病例级运行数据

### 2. 病例工作台

职责：

- 创建和选择病例
- 把中台资产绑定到某个病例
- 为病例确定本次手术上下文和病例工作包

约束：

- 可以绑定多个骨骼资产
- 可以绑定多个探针/器械资产
- 可以为每个器械或探针绑定对应几何文件
- 不负责执行配准和实时导航

### 3. 手术导航工作区

职责：

- 只读取病例已绑定的数据
- 推进准备、规划、配准、导航、评估五环节
- 保存五环节正式结果
- 管理页面恢复和实时运行态展示

约束：

- 不允许首次导入骨骼资产
- 不维护资产主数据
- 只消费病例工作包并产生病例运行结果

## 关键数据关系

### 1. 骨骼 STL 的归属

- 骨骼 STL 属于数据中台资产层
- 病例只保存“绑定了哪些骨骼资产”
- 导航工作区只保存“这些骨骼在本病例、本次流程中产生了什么结果”

### 2. 病例与骨骼的关系

- 一个病例可以绑定多个骨骼资产
- 一个骨骼资产也可以被多个病例复用
- 这是一种引用关系，不是复制拥有关系

### 3. 导航工作区与骨骼的关系

- 导航工作区读取病例已绑定的多个骨骼资产
- 规划阶段从多个骨骼中确定目标骨和目标区域
- 配准阶段按骨或骨部位分别做配准
- 导航阶段在融合后的统一导航空间中消费这些结果

## 四层数据模型

### 1. 资产层

归属：数据中台

建议实体：

- `bone_asset`
- `instrument_asset`
- `probe_asset`
- `geometry_asset`

建议字段：

- `asset_id`
- `asset_type`
- `display_name`
- `source_path`
- `normalized_path`
- `version`
- `status`
- `metadata`

### 2. 病例绑定层

归属：病例工作台

建议实体：

- `case_manifest`
- `case_asset_bindings`

建议字段：

- `case_id`
- `patient_id`
- `patient_name`
- `bound_bone_asset_ids[]`
- `bound_instrument_asset_ids[]`
- `instrument_geometry_bindings[]`
- `active_bone_scope[]`
- `active_instrument_scope[]`

### 3. 工作区运行层

归属：手术导航工作区

建议实体：

- `preparation_state`
- `planning_result`
- `per_bone_registration_results`
- `fused_navigation_space`
- `navigation_run`
- `evaluation_report`

关键要求：

- 配准结果不能再抽象为单个病例单矩阵
- 必须支持：
  - 多骨
  - 分骨部位
  - 每块骨独立配准结果
  - 融合后的统一导航空间

### 4. 恢复快照层

归属：手术导航工作区

建议实体：

- `workspace_snapshot`

作用：

- 恢复当前页签
- 恢复当前活动骨与活动器械
- 恢复最近一次阶段摘要
- 恢复最近一次门禁阻塞原因

约束：

- 不是正式业务结果
- 不可直接作为门禁真源
- 恢复后必须基于正式结果与实时状态重新计算门禁

## 五环节业务规格

### 1. 准备

目标：

- 让当前病例进入可规划、可配准状态

输入：

- 病例已绑定骨骼资产集合
- 病例已绑定探针/器械资产集合
- 每个器械或探针对应几何文件

动作：

- 选择活动骨集合
- 选择参与导航的探针和器械
- 绑定几何文件
- 对探针和所有参与导航的器械逐个标定

产物：

- 活动骨集合
- 活动器械集合
- `器械实例 -> 几何文件 -> 标定结果` 映射

### 2. 规划

目标：

- 只产出导航准备型规划结果

输入：

- 活动骨集合

动作：

- 选择目标骨
- 定义目标区域
- 定义解剖约束区
- 生成推荐配准点顺序

产物：

- `target_bone`
- `target_region`
- `anatomical_constraint_regions`
- `recommended_registration_point_order`

### 3. 配准

目标：

- 先做分骨/分部位配准，再融合成统一导航空间

输入：

- 规划结果
- 已标定探针/器械
- 当前骨或骨部位
- 服务配准黑盒

动作：

- 按骨或骨部位采点
- 对每个骨或部位独立求解配准
- 汇总独立结果
- 融合为统一导航空间

产物：

- `per_bone_registration_results[]`
- `fused_navigation_space`
- `fusion_quality_metrics`

### 4. 导航

目标：

- 在单一 3D 虚拟空间中完成实时导航

输入：

- 活动骨骼 STL
- 当前探针/器械 STL
- 统一导航空间
- 实时跟踪位姿

动作：

- 实时跟踪
- 更新 STL 位姿
- 显示空间中的实时移动和姿态变化

首版最低显示要求：

- 骨骼 STL
- 当前探针/器械 STL
- 实时位姿变化

### 5. 评估

目标：

- 对本次流程形成可追溯的评估结果

输入：

- 分骨/分部位配准结果
- 融合结果
- 导航运行记录

动作：

- 统计误差指标
- 汇总分骨/分部位配准质量
- 汇总导航过程摘要
- 生成最终评估报告并导出

产物：

- `error_metrics`
- `per_bone_quality_summary`
- `navigation_process_summary`
- `evaluation_report`

## 流程门禁原则

系统采用“允许浏览、限制执行、明确原因”的门禁策略。

规则：

- 所有页签允许进入
- 未满足前置条件时只能查看，不能执行关键动作
- 关键动作按钮禁用
- 页面结果区必须显示未就绪原因
- 状态栏必须汇总当前阻塞条件

这意味着系统不是强制禁止用户切换页签，而是让用户始终看见当前位置与阻塞原因。

## 服务配准边界

“服务配准”创新算法在首版规格中按黑盒服务处理。

首版规格只定义：

- 何时调用
- 输入数据结构
- 输出数据结构
- 成功/失败判断
- 质量门禁所依赖的指标

首版规格不展开：

- 算法内部流程
- 参数求解细节
- 内部实验框架

## 目录与持久化建议

### 资产主库

- `data/assets/bones/...`
- `data/assets/instruments/...`
- `data/assets/geometries/...`

### 病例绑定

- `data/cases/<case_id>/case_manifest.json`
- `data/cases/<case_id>/case_asset_bindings.json`

### 工作区结果

- `data/cases/<case_id>/preparation/preparation_state.json`
- `data/cases/<case_id>/planning/planning.json`
- `data/cases/<case_id>/registration/per_bone_registration_results.json`
- `data/cases/<case_id>/registration/fused_navigation_space.json`
- `data/cases/<case_id>/navigation/navigation_run.json`
- `data/cases/<case_id>/evaluation/evaluation_report.json`

### 页面恢复快照

- `data/cases/<case_id>/navigation/workspace_snapshot.json`

## 恢复原则

重进导航工作区时按以下顺序恢复：

1. 读取病例绑定层
2. 读取正式运行结果
3. 读取页面恢复快照
4. 基于正式结果和实时服务状态重新计算门禁
5. 刷新页面显示

恢复语义：

- 历史快照回答“上次做到哪里”
- 正式结果回答“已经产出了什么”
- 实时状态回答“当前还能不能继续”

## 验收标准

首版完成后必须满足：

1. 骨骼 STL 首次导入入口只在数据中台
2. 病例工作台可以为病例绑定多个骨骼、多个探针/器械与对应几何文件
3. 手术导航工作区只能消费病例已绑定资产
4. 五环节全部可进入，但未满足前置时只能查看不能执行
5. 准备阶段能完成探针和所有参与导航器械的几何绑定与标定
6. 规划阶段能输出目标骨、目标区域、解剖约束区、推荐配准点顺序
7. 配准阶段能输出分骨结果集与融合导航空间
8. 导航阶段是单一 3D 虚拟空间，并可显示骨骼与工具的实时位姿
9. 评估阶段能输出误差指标、分骨质量、导航过程摘要和导出报告
10. 页面恢复后会基于实时状态重新判断是否允许继续流程

## 成功判定

这份架构设计成功落地的标志是：

- 系统正式形成“资产主库、病例绑定、工作区运行、页面快照”四层边界
- 骨骼 STL、病例和导航工作区之间的关系不再混淆
- 五环节从“页面动作集合”升级为“病例驱动的手术工作流”
- 后续导航工作区内部改造可以在清晰上层约束下进行

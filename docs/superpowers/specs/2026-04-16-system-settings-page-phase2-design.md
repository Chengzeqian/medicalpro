# SystemSettingsPage Phase 2 Design

日期：2026-04-16
范围：`SystemSettingsPage` 产品化视觉升级与“状态先行 + 配置随后”双层页重构
目标：在不改变现有页面跳转、不新增高风险交互、不改 `QSettings` 键和现有设置项的前提下，把 `SystemSettingsPage` 从旧式表单页升级为与 `Welcome -> ModuleSelection -> Management -> Dashboard` 同一视觉语言下的辅助检查工作台。

## 1. 页面定位

`SystemSettingsPage` 不应继续只是“系统配置表单”，而应被定义为：

> 在进入后续主流程前，先确认当前环境是否健康，再调整当前运行配置的辅助入口页。

它在主链中的职责是：
- 承接 `ModuleSelectionPage` 中的辅助入口
- 先给用户清晰的系统状态判断
- 再允许用户调整语言、主题、设备与路径配置
- 最后把用户自然送回模块页，而不是抢主流程入口的权重

本页不是：
- 主流程页
- 重型运维控制台
- 多步骤向导页

## 2. 当前现状

### 2.1 现有基础
- 页面类：`UI/NewPages/SystemSettingsPage.cpp`
- UI 文件：`UI/Forms/SystemSettingsPage.ui`
- 当前已具备基础功能：
  - 语言、主题、自动保存
  - 追踪器端口、波特率
  - 数据路径、DICOM 路径
  - 浏览目录与保存设置
- 当前跳转关系已经成立：
  - `ModuleSelectionPage -> SystemSettingsPage`
  - `SystemSettingsPage -> ModuleSelectionPage`

### 2.2 当前问题
- 视觉结构仍是旧式 `QGroupBox + QFormLayout` 表单页
- 样式大量写死在 `.ui` 文件内，未接入 `three_pages_theme.qss`
- 页面进入后第一眼看到的是“要填什么”，而不是“当前环境是否正常”
- 和已经完成 Phase 2 收口的 `Welcome / ModuleSelection / Management / Dashboard` 放在一起时，像另一套系统
- `浏览` 按钮、`保存` 按钮与表单区主次关系不清晰
- 页面缺少“当前建议”，无法明确告诉用户应该先检查什么

## 3. 设计方向选择

本轮已确认采用：

> 方案 2：系统状态 + 配置表单双层页面

即：
- 上半部分先看系统状态
- 下半部分再改配置

不采用其他方向的原因：
- 纯表单页升级太弱，承接不了模块页“辅助入口”的语义
- 运维控制台型改造过重，会破坏当前入口链的主次
- 分段向导会把长期设置页做得过于流程化，不适合反复进入使用

## 4. 页面结构

建议将页面重构为四个阅读层级：

### 4.1 顶部 Header
职责：定义本页身份与主操作

组成：
- 左侧：`返回模块页`
- 中部：页面标题与副标题
- 右侧：`保存设置`

文案：
- 眉题：`SYSTEM HEALTH & CONFIG`
- 标题：`系统设置与环境检查`
- 副标题：`先确认插件、服务与路径状态，再调整当前运行配置。`

要求：
- `保存设置` 是页面主 CTA
- `返回模块页` 是次按钮
- Header 风格与 `ManagementPage`、`DashboardPage` 保持统一，但要更像辅助检查台

### 4.2 状态总览区
职责：第一眼回答“当前环境是否健康”

采用三张状态卡并排：
- 插件框架
- 关键服务
- 数据与影像路径

每张卡结构统一为：
- 状态标签
- 一句主结论
- 一句简短说明

信息组织原则：
- 不展示过多技术细节
- 只展示用户是否可继续、应优先检查什么
- 文案长度保持短促、可扫描

### 4.3 当前建议条
职责：明确用户“现在该做什么”

位置：状态总览区下方，配置表单区上方

默认语气：
- 正常：`当前环境可继续使用，如需微调参数可直接保存。`
- 警告：`建议先检查关键服务与路径状态，再继续主流程。`
- 异常：`当前更适合先排查环境问题，不建议直接进入后续流程。`

要求：
- 这是本页和纯表单页拉开差异的核心元素
- 语气要像“辅助判断”，不要像“报错弹窗”

### 4.4 配置表单区
职责：在状态判断之后，承接实际配置编辑

保留现有设置项，但重组为三张产品化配置卡：
- 常规设置
- 设备连接
- 路径配置

每张配置卡结构：
- 卡片标题
- 一句说明
- 表单控件

配置卡内容映射：
- 常规设置
  - 语言
  - 主题
  - 自动保存
- 设备连接
  - 追踪器端口
  - 波特率
- 路径配置
  - 数据路径
  - DICOM 路径
  - 对应浏览按钮

## 5. 视觉语言

### 5.1 总体风格
延续当前四页已经稳定下来的深蓝工作台风格，不换主题，不引入新设计体系。

但本页要和其他页面做轻微角色区分：
- 比 `ManagementPage` 更轻、更明确
- 比 `ModuleSelectionPage` 更稳、更规整
- 比纯设置页更有“系统检查台”的气质

### 5.2 层级重点
阅读优先级应为：
1. Header 标题区
2. 状态总览区
3. 当前建议条
4. 配置表单区
5. 浏览等次级按钮

### 5.3 状态卡风格
状态卡要比下方表单卡更显眼，但不能压过 Header。

建议强调顺序：
- 状态 badge
- 主结论
- 简短说明

颜色策略：
- `ok`：沿用现有成功色
- `warning`：沿用现有警告色
- `danger`：沿用现有异常色

### 5.4 配置卡风格
配置卡使用更稳的深色卡片语言：
- 卡片标题更突出
- 说明文案较轻
- 输入控件统一高度与圆角
- `浏览` 按钮统一降级，不与 `保存设置` 抢主次

## 6. 文案规范

### 6.1 Header 文案
- 眉题：`SYSTEM HEALTH & CONFIG`
- 标题：`系统设置与环境检查`
- 副标题：`先确认插件、服务与路径状态，再调整当前运行配置。`

### 6.2 状态总览卡标题
- `插件框架`
- `关键服务`
- `数据与影像路径`

### 6.3 配置卡标题与说明
- 常规设置
  - `调整语言、主题与自动保存策略。`
- 设备连接
  - `确认当前追踪器串口与通信参数。`
- 路径配置
  - `核对数据目录与 DICOM 目录是否可访问。`

### 6.4 操作文案
- 主按钮：`保存设置`
- 次按钮：`返回模块页`
- 路径按钮：`浏览`

## 7. 运行状态来源

本轮不新增高风险状态链，只读取当前代码里已经可获得或可轻量补齐的运行状态：

- 插件框架状态
  - 优先复用现有 CTK 可用性判断逻辑
- 关键服务状态
  - 参考 `WelcomePage` / `ModuleSelectionPage` 已在使用的服务缺失判断
- 路径状态
  - 基于当前 `dataPathEdit`、`dicomPathEdit` 的文本值做目录可访问性检查

本轮不做：
- 新插件管理器
- 新后台线程
- 深度服务探针
- 高风险异步状态面板

## 8. 实施边界

本轮明确不做以下内容：
- 不改变页面跳转关系
- 不改变现有设置项
- 不改变现有 `QSettings` key
- 不修改插件链与服务链核心逻辑
- 不引入新第三方 UI 库
- 不把页面升级为重型运维控制台

本轮优先实现手段：
- `.ui` 重排
- `SystemSettingsPage.cpp` 补运行摘要与文案
- `UI/styles/three_pages_theme.qss` 增加 `SystemSettingsPage` 专属样式
- 尽量清除 `.ui` 中旧式内联样式，让主题层接管视觉

## 9. 验收标准

本轮完成后，应满足：
- 用户进入页面第一眼先看到“当前环境是否健康”
- 用户第二眼才看到“能改哪些设置”
- 页面风格与 `ModuleSelectionPage` 的辅助入口定位一致
- 与 `Welcome / ModuleSelection / Management / Dashboard` 一起看时，不会像另一个系统
- `保存设置` 明确是主操作，`浏览` 明确是次级操作
- 页面保持当前功能项完整，无跳转回归、无设置项丢失

## 10. 后续实现建议

本 spec 审核通过后，下一步进入实现计划时建议拆成四段：
1. 页面结构与 `.ui` 重排
2. 状态总览与建议条接入
3. 公共 `QSS` 接管 `SystemSettingsPage`
4. 构建、回归测试与真实启动验证

## 11. 2026-04-16 基于真实运行图的下一轮视觉验收反馈

在 Phase 2 第一轮落地并看到真实运行图之后，当前页面已经具备正确的信息顺序，但仍存在以下视觉问题：

- `Header` 结构正确，但整体偏薄，更像工具栏而不是正式的系统检查台页头
- 三张状态卡现在偏横向、偏扁，信息被压平，没有充分承担“状态先行”的首屏主视觉职责
- 当前建议条更像一根长提示条，而不是一个清晰的“当前判断结果”
- 下半区三张配置卡虽然已经接入统一主题，但仍偏长表单感，和首屏之间的主次关系还不够清楚
- 页面底部仍有较明显的大留白，影响整体完成度

因此，本轮后续视觉微调不再改变 Phase 2 的页面结构方向，而是在现有结构上继续做“首屏强化 + 配置区降级”的验收向收口。

## 12. 本轮微调方向

本轮已确认采用：

> 方向 A：首屏强化

即：
- 优先强化 `Header + 状态总览 + 当前建议`
- 让用户在进入页面后的第一屏内快速完成状态判断
- 再让下半区配置卡承接编辑任务，而不是和首屏争主视觉

不优先采用其他方向的原因：
- 单独先做表单密度，只能改善编辑区，不足以解决首屏重心偏弱的问题
- 单独先做风格精修，只会让页面更“细”，但不会让页面更“对”
- 当前问题的核心不是缺样式，而是首屏层级还没有完全立起来

## 13. 本轮微调设计

### 13.1 首屏结构重心

本轮不改页面功能和跳转，只强化页面前 3 秒可读性，目标是让用户进入页后能快速看懂：

- 当前系统环境是否健康
- 当前更适合继续主流程，还是先排查环境
- 配置编辑属于第二优先级动作

首屏阅读顺序固定为：
1. 页面身份
2. 三个核心状态
3. 当前建议
4. 配置编辑

完成后应形成“系统检查台”而不是“配置工具页”的第一印象。

### 13.2 Header 微调

本轮 `Header` 的目标不是改结构，而是强化身份感：

- 整体高度再抬一档，做成更完整的页头卡片
- 主标题 `系统设置与环境检查` 再增加一档权重与尺寸
- 副标题宽度收住，避免横向铺得过散
- `返回模块页` 继续作为次按钮，但视觉体量略轻，避免和主标题抢注意力
- `保存设置` 继续作为唯一主 CTA，尺寸与色块强度保持第一优先级

页面进入后的第一视觉焦点应先落在标题区，而不是右上角按钮。

### 13.3 状态总览卡微调

三张状态卡继续保持并排，但要从“横向扁信息块”升级为“首屏状态摘要卡”：

- 整体高度上提，减少被压扁的感觉
- 卡内阅读顺序固定为：
  - 小标题
  - 短 badge
  - 主结论
  - 一句说明
- `badge` 做成短胶囊，不再呈现近似进度条的横向拉伸感
- 主结论字体再上提一档，承担卡内第一视觉焦点
- 说明文案尽量控制在两行以内，强调“可扫读”而不是“信息堆积”

这三张卡必须真正承担“状态先行”的首屏主视觉，而不只是系统说明的附属块。

### 13.4 当前建议条微调

当前建议条继续保留在状态卡下方，但语义上要更像“判断结果卡”：

- 不再追求一根长横条的提示感
- 左侧保留状态 badge，右侧是一句明确结论
- 整体高度略高于当前版本，但仍低于状态卡
- 语气保持辅助判断，不做报错弹窗式恐吓

本区的定位是：

> 在三张状态卡之后，给出一句清晰的“现在建议怎么做”。

### 13.5 配置区层级收口

下半区继续保留：
- `常规设置`
- `设备连接`
- `路径配置`

但本轮要明确降级为“状态判断之后的编辑区”：

- 视觉权重低于首屏，不再与状态卡争夺第一焦点
- 三张卡之间的上下间距收紧，避免页面被继续拉长
- 每张卡的“标题 + 说明”关系更贴近，减少头部虚空感
- 表单行高略增，让控件更稳，但卡片本身不继续无意义变高

### 13.6 表单密度与路径区收口

本轮配置区重点优化密度与整齐度：

- 标签列与输入列的距离略缩短
- 输入框、下拉框、按钮保持更统一的基线
- `路径配置` 两行路径项的按钮宽度统一，不要显得零散
- `自动保存` 一行避免过空，勾选项和标签要更像一个整体
- 页面底部大留白直接收掉，让 `路径配置` 卡结束后页面自然收尾

目标不是把页面塞满，而是让页面完整结束，不出现“内容没有排满画布”的感觉。

## 14. 本轮实施边界

本轮只处理 `SystemSettingsPage` 的视觉层级微调，不改变以下内容：

- 不改变页面跳转关系
- 不改变现有设置项
- 不改变现有 `QSettings` key
- 不碰插件链、服务链和启动链逻辑
- 不引入新第三方库
- 不把页面升级为新的功能页或运维页

本轮允许的实现落点：

- `UI/Forms/SystemSettingsPage.ui`
- `UI/styles/three_pages_theme.qss`
- 如有必要，少量调整 `UI/NewPages/SystemSettingsPage.cpp` 的文案或布局配合
- 同步更新相关设计文档与状态文档

## 15. 本轮验收标准

本轮微调完成后，应满足：

- 用户进入页面后，第一眼先看到更稳的页头和更明确的状态总览
- 三张状态卡不再显得过扁、过散，而是真正成为首屏主视觉
- 当前建议条更像“当前判断结果”，而不是普通长横条提示
- 下半区三张配置卡层级更清楚，不再和首屏争第一焦点
- 表单区更紧凑、更整齐，尤其路径区和浏览按钮更统一
- 页面底部大留白明显收掉，整体完成度更高
- 所有功能行为保持不变，没有跳转、设置读写和状态展示回归
